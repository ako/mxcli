# Proposal: owning the `modelsdk/gen` codegen

**Status:** Draft
**Date:** 2026-08-13
**Author:** Generated with Claude Code

This closes the last open Phase-0 item of
[`docs/plans/2026-06-05-adopt-modelsdk-engine.md`](../plans/2026-06-05-adopt-modelsdk-engine.md)
§4 — *"Vendor engalar codegen + `TypeVersionInfo` type-level bound fix — ⏳ todo"* —
and records why the answer turned out to be **not to vendor it**.

The adoption plan assumed the generator was a missing piece to be copied over.
It is not: the generator works, and its **input** is what makes ~100 properties
wrong. Copying it in would give us the ability to regenerate and would
reintroduce the defects on every run. This proposal states the measurements,
the decision, and what to do instead.

It does not re-litigate the engine adoption itself. That is
[ADR-0004](../13-decisions/0004-full-codec-engine.md) and
[ADR-0005](../13-decisions/0005-semantic-model-interface-currency.md); the write-path
harvest question is
[`ASSESSMENT_harvest_engalar_writes.md`](ASSESSMENT_harvest_engalar_writes.md).

## 1. What we actually inherited

`modelsdk/gen` — 224 files, ~129k lines — was cherry-picked from engalar's fork
as **output**. The header on every file names tooling that has never existed in
this repository:

```go
// Code generated by mxcli codegen; DO NOT EDIT.
// To modify: edit internal/codegen/supplements.json or internal/codegen/emitter/templates.go,
// then run: go run ./cmd/modelsdk-codegen
```

`git log --all` is empty for both `cmd/modelsdk-codegen` and
`internal/codegen/supplements.json`. The generator lives on engalar's fork as
`cmd/codegen` (with `audit.go`, whose `audit-keys` mode the adoption plan wanted
promoted to a CI gate). It is reachable; it was simply never brought over.

We also have a **second, unrelated** generator that we do own: `cmd/codegen` →
`generated/metamodel`. The two are easily confused because they share a
directory name across the two repositories.

## 2. The two generators read different inputs — this is the whole story

| | `cmd/codegen` (ours) | `cmd/codegen` (engalar's fork) |
|---|---|---|
| input | `reflection-data/{version}-structures.json` | `node_modules/mendixmodelsdk/src/gen/*.js` |
| input is | Mendix **reflection data** | the **TypeScript SDK**, compiled |
| output | `generated/metamodel` (~12k lines) | `modelsdk/gen` (~129k lines) |
| storage names | **in the data** (`storageName` per property) | **absent** — patched by hand via `PropertyKeyOverrides` in `supplements.json` |

Mendix maintains two names per property: an SDK-facing `Name` and the
`StorageName` that is the actual BSON key (the property-level twin of the
`$Type` storage-name table in CLAUDE.md — `ShowPageAction` is stored as
`ShowFormAction`).

Our generator has both and keeps them apart — Go field name from `Name`, json
tag from `StorageName`:

```go
// generated/metamodel/types.go
RegularExpression model.QualifiedName `json:"regExIdentifier,omitempty"`
//   ^ SDK name                                ^ storage name
```

The TypeScript SDK has only the first. Measured directly against the published
package (`mendixmodelsdk` 4.114.0, `src/gen/domainmodels.js`):

```js
this.__regularExpression = new internal.ByNameReferenceProperty(
    RegExRuleInfo, this, "regularExpression", null, "RegularExpressions$RegularExpression");
```

`regExIdentifier` occurs **0 times** in that file. The storage name is not
merely unused by the generator — it is **not present in its input**.

That is why `supplements.json` carries a `PropertyKeyOverrides` table at all: it
is a hand-maintained patch list compensating for information the input lacks,
and it covers only what someone happened to hit.

### 2.1 The resulting defect, quantified

`modelsdk/gen/keyaudit_test.go` cross-checks every property key gen binds
against the storage name `generated/metamodel` records. Of **571** types
cross-checkable, **65 carry at least one wrong key — 102 properties in total**.

Three have independent confirmation, and all three are flagged correctly by the
audit, which is what makes it worth trusting on the rest:

| property | gen binds | Mendix stores | how it was confirmed |
|---|---|---|---|
| `RegularExpressions$RegularExpression` pattern | `RegEx` | `Expression` | five Studio Pro documents (Email Connector 6.4.2, Community Commons 11.5.1) |
| `DomainModels$RegExRuleInfo` reference | `RegularExpression` | `RegExIdentifier` | mxbuild 11.13 reports **CE0135 "No regular expression specified"** on the wrong key; 0 errors on the right one |
| `DomainModels$Attribute` / `Association` GUID | `DataStorageGuid` | `GUID` | already worked around in `modelsdk/codec/encoder.go` (`EmitGUID`); see `issue657_guid_test.go` |

The GUID one is the measure of the stakes: per CLAUDE.md, an entity's `GUID` is
the runtime's database identity, and losing it destroys the entity's rows on
next deploy.

## 3. Are we regenerating per Mendix version? No — and the two trees differ

Worth stating plainly, because the two generated trees have **different
versioning models** and only one of them is stale.

**`modelsdk/gen` is version-parametric, not per-version.** 53 `version.go` files
carry per-property `Introduced`/`Deleted` bounds, evaluated at runtime by
`modelsdk/version`:

```go
"DomainModels$AssociationBase": {Properties: map[string]version.PropertyVersionInfo{
    "capabilities":  {Introduced: "8.11.0", Deleted: "9.0.1", Required: true, Public: true},
    "storageFormat": {Introduced: "10.21.0", Public: true},
}},
```

One generation therefore covers Mendix 8 through 11. Regeneration is needed only
when a Mendix release **adds** types or properties — not on every minor. This is
a good design and is a further argument for keeping the tree rather than
churning it.

The known gap, inherited and still open: the plan's *"`TypeVersionInfo`
type-level bound fix"* — the parser captures type-level `Introduced`/`Deleted`
but the emitted struct drops it, so a whole type introduced in a later version
carries no bound.

**`generated/metamodel` is a snapshot, and it is stale.** Its header reads
`Source: 11.6.0-structures.json`, while the toolchain in use here is 11.13.0 —
seven minors behind. Two consequences:

- Storage names are stable by construction (the SDK/storage split exists so the
  SDK-facing name can change without disturbing storage), so an 11.6.0 snapshot
  is sound evidence **for the properties it contains**.
- It is **not** authoritative for anything introduced after 11.6. Any audit
  finding involving a newer property needs a document, not the snapshot.

This qualifies the "`generated/metamodel` is the arbiter" rule in CLAUDE.md, and
it is a reason to fix provenance (§4) rather than lean on the snapshot forever.

## 4. The blocker: the input is not in the repository, and not public

Both generators are unrunnable here today.

- `/reference/` is gitignored (`.gitignore:37`, plus `reference/mendixmodellib/`
  explicitly at line 34), so `reference/mendixmodellib/reflection-data/` — named
  by `BSON_TOOLING_GUIDE.md` §"Reflection data reference" and
  `PAGE_BSON_SERIALIZATION.md` as *the* authoritative source — is absent.
- `npm registry mendixmodellib` → **404**. A registry search for Mendix model
  packages returns the TypeScript SDK, the Platform SDK, widget tooling and
  third-party wrappers; **nothing publishes reflection/structures JSON**.
- It is not in the mxbuild distribution we already download per version, at
  least not as JSON: no `*structures*` or `*reflection*` file exists anywhere in
  `mxbuild/11.13.0/`. (Mendix's metamodel does live in the modeler assemblies —
  ADR-0008 notes `IsIdentifier` is only reachable there — so extraction from the
  `.dll`s may be possible, but that is a research task, not a dependency bump.)

**So the input we want is not the input that is public.** `mendixmodelsdk` is
public, downloads cleanly, and is exactly the source that lacks storage names.
Pulling it on every Mendix release would keep gen current and keep it wrong.

Establishing the provenance of `reflection-data` is therefore the crux, and it
is the one genuinely open question in this proposal.

## 5. Decision

**Do not vendor engalar's generator.** It would let us regenerate and would
reintroduce the 102 mismatches on every run, behind a `supplements.json` we
would then have to grow to 102 entries by hand — the same work as patching gen
directly, with an extra moving part.

**Fix a wrong key by hand, in `init<Type>`, with the evidence in the comment.**
Four such `STORAGE-NAME OVERRIDE` precedents already exist, and
`TestGeneratedCodeIsFormatted` exists *because* gen files get hand-edited. Two
rules, both already violated once:

1. **Patch both literals.** The encode key (`init<Type>`) and the decode key
   (`InitFromRaw`) are separate. Patching one yields a document that writes one
   key and reads another; the symptom is a confusing entity-rewrite refusal
   rather than a bad file.
2. **`gofmt` the file.**

**Do not fix all 102.** Most belong to types nothing writes, and a fix without
per-property evidence is a guess in the same class as the bug. The ledger in
`keyaudit_test.go` records them and fails on the two things that matter: a new
mismatch appearing (a re-vendored gen that silently dropped an override —
otherwise invisible until a user's document loses a property) and a listed one
being fixed without being struck off.

**`mx check` is a weak oracle here.** It caught the `RegExIdentifier` case as
CE0135, but it tolerates unknown properties in general, and Studio Pro is
stricter than mxbuild (CLAUDE.md, "Overlay Writes"). A green build is not
evidence that a key is right.

## 6. Proposed sequence

Ordered by dependency; each step is worth doing on its own.

1. **Establish `reflection-data` provenance.** Where does
   `reference/mendixmodellib/` come from, is redistribution permitted, and how
   large is it? Until this is answered, neither generator can be run here and
   `generated/metamodel` cannot be refreshed off 11.6.0. *Blocks 2 and 4.*
2. **Vendor the reflection data** (just `reflection-data/`, not the mxbuild
   binaries also under `/reference/`), and add a `make` target to refresh it.
   This alone makes `generated/metamodel` regenerable and the CLAUDE.md arbiter
   claim verifiable.
3. **Promote the audit to a build-time gate.** `keyaudit_test.go` already runs
   in `go test`; the remaining work is deciding whether a new mismatch should
   fail CI hard. Cheap, and independent of 1.
4. **Then, optionally, emit the codec shape from our own generator.** A second
   emitter on `cmd/codegen` would make all 102 correct *by construction* rather
   than by an override table, and would fold in the `TypeVersionInfo` type-level
   bound fix. This is the largest item by far: the emitter must reproduce the
   codec registrations (`TypeDefaults`, list markers) and the existing hand
   overrides. Do not start it before 1–3, and not before spot-checking more of
   the 102 against real documents — three confirmed out of 102 is thin support
   for a wholesale regeneration.
5. **Report upstream.** The ledger is a concrete bug list against Mendix's own
   SDK-to-storage mapping, and the real fix belongs in the generator, wherever
   it is maintained.

## 7. What this does not change

- No change to the engine split, the backend interface, or ADR-0004/0005.
- No change to `modelsdk/gen`'s versioning model — it stays version-parametric.
- Existing `STORAGE-NAME OVERRIDE` patches stay as they are.

## 8. Open questions

1. **`reflection-data` provenance and licence.** The blocker in §4.
2. **Can it be extracted from the modeler assemblies?** That would give us the
   input per Mendix version from a distribution we already download, which would
   be the ideal outcome — and would also settle ADR-0008's note that
   `IsIdentifier` is only available there.
3. **How many of the remaining 102 matter?** A cheap first pass: intersect the
   ledger with the `$Type`s mxcli actually writes.
4. **Should the audit compare against a Studio Pro document corpus** rather than
   `generated/metamodel`, given §3's staleness caveat? Marketplace modules are
   already used this way for scheduled events and regular expressions.
