# Proposal: owning the `modelsdk/gen` codegen

**Status:** Draft
**Date:** 2026-08-13
**Author:** Generated with Claude Code

**Constraint set by the maintainer (2026-08-13):** the reflection data is an
internal closed-source Mendix library, so it is unusable as a dependency for an
open-source project regardless of technical fit. §4A is the licence-clean
replacement.

This closes the last open Phase-0 item of
[`docs/plans/2026-06-05-adopt-modelsdk-engine.md`](../plans/2026-06-05-adopt-modelsdk-engine.md)
§4 — *"Vendor engalar codegen + `TypeVersionInfo` type-level bound fix — ⏳ todo"* —
and records why the answer turned out to be **not to vendor it**.

The adoption plan assumed the generator was a missing piece to be copied over.
It is not: the generator works, and its **input** is what makes ~100 properties
wrong. Copying it in would give us the ability to regenerate and would
reintroduce the defects on every run. This proposal states the measurements,
the decision, and what to do instead.

It does not re-litigate the engine adoption itself. That is
[ADR-0004](../13-decisions/0004-full-codec-engine.md) and
[ADR-0005](../13-decisions/0005-semantic-model-interface-currency.md); the write-path
harvest question is
[`ASSESSMENT_harvest_engalar_writes.md`](ASSESSMENT_harvest_engalar_writes.md).

## 1. What we actually inherited

`modelsdk/gen` — 224 files, ~129k lines — was cherry-picked from engalar's fork
as **output**. The header on every file names tooling that has never existed in
this repository:

```go
// Code generated by mxcli codegen; DO NOT EDIT.
// To modify: edit internal/codegen/supplements.json or internal/codegen/emitter/templates.go,
// then run: go run ./cmd/modelsdk-codegen
```

`git log --all` is empty for both `cmd/modelsdk-codegen` and
`internal/codegen/supplements.json`. The generator lives on engalar's fork as
`cmd/codegen` (with `audit.go`, whose `audit-keys` mode the adoption plan wanted
promoted to a CI gate). It is reachable; it was simply never brought over.

We also have a **second, unrelated** generator that we do own: `cmd/codegen` →
`generated/metamodel`. The two are easily confused because they share a
directory name across the two repositories.

## 2. The two generators read different inputs — this is the whole story

| | `cmd/codegen` (ours) | `cmd/codegen` (engalar's fork) |
|---|---|---|
| input | `reflection-data/{version}-structures.json` | `node_modules/mendixmodelsdk/src/gen/*.js` |
| input is | Mendix **reflection data** | the **TypeScript SDK**, compiled |
| output | `generated/metamodel` (~12k lines) | `modelsdk/gen` (~129k lines) |
| storage names | **in the data** (`storageName` per property) | **absent** — patched by hand via `PropertyKeyOverrides` in `supplements.json` |

Mendix maintains two names per property: an SDK-facing `Name` and the
`StorageName` that is the actual BSON key (the property-level twin of the
`$Type` storage-name table in CLAUDE.md — `ShowPageAction` is stored as
`ShowFormAction`).

Our generator has both and keeps them apart — Go field name from `Name`, json
tag from `StorageName`:

```go
// generated/metamodel/types.go
RegularExpression model.QualifiedName `json:"regExIdentifier,omitempty"`
//   ^ SDK name                                ^ storage name
```

The TypeScript SDK has only the first. Measured directly against the published
package (`mendixmodelsdk` 4.114.0, `src/gen/domainmodels.js`):

```js
this.__regularExpression = new internal.ByNameReferenceProperty(
    RegExRuleInfo, this, "regularExpression", null, "RegularExpressions$RegularExpression");
```

`regExIdentifier` occurs **0 times** in that file. The storage name is not
merely unused by the generator — it is **not present in its input**.

That is why `supplements.json` carries a `PropertyKeyOverrides` table at all: it
is a hand-maintained patch list compensating for information the input lacks,
and it covers only what someone happened to hit.

### 2.1 The resulting defect, quantified

`modelsdk/gen/keyaudit_test.go` cross-checks every property key gen binds
against the storage name `generated/metamodel` records. Of **571** types
cross-checkable, **65 carry at least one wrong key — 102 properties in total**.

Three have independent confirmation, and all three are flagged correctly by the
audit, which is what makes it worth trusting on the rest:

| property | gen binds | Mendix stores | how it was confirmed |
|---|---|---|---|
| `RegularExpressions$RegularExpression` pattern | `RegEx` | `Expression` | five Studio Pro documents (Email Connector 6.4.2, Community Commons 11.5.1) |
| `DomainModels$RegExRuleInfo` reference | `RegularExpression` | `RegExIdentifier` | mxbuild 11.13 reports **CE0135 "No regular expression specified"** on the wrong key; 0 errors on the right one |
| `DomainModels$Attribute` / `Association` GUID | `DataStorageGuid` | `GUID` | already worked around in `modelsdk/codec/encoder.go` (`EmitGUID`); see `issue657_guid_test.go` |

The GUID one is the measure of the stakes: per CLAUDE.md, an entity's `GUID` is
the runtime's database identity, and losing it destroys the entity's rows on
next deploy.

## 3. Are we regenerating per Mendix version? No — and the two trees differ

Worth stating plainly, because the two generated trees have **different
versioning models** and only one of them is stale.

**`modelsdk/gen` is version-parametric, not per-version.** 53 `version.go` files
carry per-property `Introduced`/`Deleted` bounds, evaluated at runtime by
`modelsdk/version`:

```go
"DomainModels$AssociationBase": {Properties: map[string]version.PropertyVersionInfo{
    "capabilities":  {Introduced: "8.11.0", Deleted: "9.0.1", Required: true, Public: true},
    "storageFormat": {Introduced: "10.21.0", Public: true},
}},
```

One generation therefore covers Mendix 8 through 11. Regeneration is needed only
when a Mendix release **adds** types or properties — not on every minor. This is
a good design and is a further argument for keeping the tree rather than
churning it.

The known gap, inherited and still open: the plan's *"`TypeVersionInfo`
type-level bound fix"* — the parser captures type-level `Introduced`/`Deleted`
but the emitted struct drops it, so a whole type introduced in a later version
carries no bound.

**`generated/metamodel` is a snapshot, and it is stale.** Its header reads
`Source: 11.6.0-structures.json`, while the toolchain in use here is 11.13.0 —
seven minors behind. Two consequences:

- Storage names are stable by construction (the SDK/storage split exists so the
  SDK-facing name can change without disturbing storage), so an 11.6.0 snapshot
  is sound evidence **for the properties it contains**.
- It is **not** authoritative for anything introduced after 11.6. Any audit
  finding involving a newer property needs a document, not the snapshot.

This qualifies the "`generated/metamodel` is the arbiter" rule in CLAUDE.md, and
it is a reason to fix provenance (§4) rather than lean on the snapshot forever.

## 4. The blocker: the input is not in the repository, and not public

Both generators are unrunnable here today.

- `/reference/` is gitignored (`.gitignore:37`, plus `reference/mendixmodellib/`
  explicitly at line 34), so `reference/mendixmodellib/reflection-data/` — named
  by `BSON_TOOLING_GUIDE.md` §"Reflection data reference" and
  `PAGE_BSON_SERIALIZATION.md` as *the* authoritative source — is absent.
- `npm registry mendixmodellib` → **404**. A registry search for Mendix model
  packages returns the TypeScript SDK, the Platform SDK, widget tooling and
  third-party wrappers; **nothing publishes reflection/structures JSON**.
- It is not in the mxbuild distribution we already download per version, at
  least not as JSON: no `*structures*` or `*reflection*` file exists anywhere in
  `mxbuild/11.13.0/`. (Mendix's metamodel does live in the modeler assemblies —
  ADR-0008 notes `IsIdentifier` is only reachable there — so extraction from the
  `.dll`s may be possible, but that is a research task, not a dependency bump.)

**So the input we want is not the input that is public.** `mendixmodelsdk` is
public, downloads cleanly, and is exactly the source that lacks storage names.
Pulling it on every Mendix release would keep gen current and keep it wrong.

### 4.1 Reflection data is disqualified on licence, not availability

`reference/mendixmodellib/` is an **internal, closed-source Mendix library**. Even
where a copy exists, building mxcli's correctness on it would mean the project
could only be developed by people holding that artefact — which is
disqualifying for an open-source community regardless of the technical fit.

This proposal therefore does **not** recommend vendoring it, and the
"`generated/metamodel` is the arbiter" rule should be treated as a **transitional**
position: it is the best evidence currently in the tree (and it produced the
three confirmed fixes), but it rests on an input we cannot refresh or
redistribute, and it is pinned at 11.6.0.

## 4A. The replacement: derive storage names from documents, not from reflection data

Documents beat reflection data — that is already this repository's own rule,
proven three times (CLAUDE.md, "when gen and an observed document disagree, the
document wins"). Storage names are directly observable in Studio Pro's own
serializer output, which is stronger evidence than any type table and is not
encumbered.

### 4A.1 What the Studio Pro MCP server can and cannot do here

`ped_get_schema` is keyed by BSON `$Type` (`{"types":["DomainModels$Entity"]}`)
and knows types PED cannot even read as documents — security elements, per
`PED_MCP_CAPABILITIES.md`. mxcli already calls it, purely to satisfy PED's
fetch-before-create contract, and **discards the body**.

It is nonetheless unlikely to answer the storage-name question, because **PED
speaks a Studio-Pro-facing vocabulary, not the storage one**. The clearest
evidence is mxcli's own PED wire format:

```go
// mdl/backend/mcp/domainmodel.go
type pedAttribute struct {
	SType           string `json:"$Type"`
	Name            string `json:"name"`
	Type            string `json:"type"`   // storage key is "NewType"
	EnumerationName string `json:"enumerationName,omitempty"`
	Value           any    `json:"value,omitempty"`
}
```

`Attribute`'s type child is stored as **`NewType`** (see `modelsdk/codec/decoder.go`'s
`fieldAliases`), and in storage it is a child ELEMENT
(`DomainModels$StringAttributeType`), not the string `"String"` PED accepts.
So PED is a projection, not the storage shape. **This is inference from the wire
format, not a measurement** — confirming it needs one `ped_get_schema` call
against a live Studio Pro with the body kept, which is cheap and worth doing
before relying on either answer.

The valuable MCP capability is therefore not the schema but the **round trip**:
drive Studio Pro to author a construct via `ped_create_document` /
`ped_update_document`, then read the resulting `.mxunit`. That automates the
manual loop CLAUDE.md already prescribes ("ask the user to create a working
example in Mendix Studio Pro so you can compare the generated BSON"), and the
bytes it yields are authoritative by construction and correct for whichever
Studio Pro version is attached.

Its limits are real: it needs Windows/macOS plus an installed Studio Pro, so it
is a developer-loop tool and not a CI step; it can only observe constructs PED
is permitted to author; and it observes only properties actually **present** in
a document, so an unset optional property stays invisible.

### 4A.2 Most of it needs no Studio Pro at all

A project created by `mx create-project` is already Studio Pro output, and
mxbuild is downloaded per version by `mxcli setup mxbuild`. Measured on a blank
11.13.0 project:

| | count |
|---|---|
| `.mxunit` documents | 369 |
| distinct storage `$Type`s | 242 |
| **ledgered types (of 65) present** | **21** |

Those 21 can be checked against real bytes **today, on Linux, in CI, with no
licence and no network**. That is the floor, not the ceiling.

Caveat on the 21: a `$Type` appearing in a corpus does not guarantee the
specific mismatched **property** appears in it, so 21 is an upper bound on what
a blank app can immediately settle. Determining the real figure is the first
task in §6.

### 4A.3 Richer corpora: marketplace modules, and whole sample apps

A blank app is thin by construction — it instantiates almost no microflow
activities, no workflows, no REST, no mappings, which is exactly where the long
tail of the ledger lives (`Microflows$ImportMappingCall`, `Rest$ODataRemoteEntitySource`,
`WebServices$PublishedParameter`, …). Three sources extend it, in increasing
order of coverage:

1. **Marketplace modules** — already the established method. The
   regular-expression codec is pinned against five Studio Pro documents from
   Email Connector 6.4.2 and Community Commons 11.5.1; the scheduled-event codec
   against three from Workflow Commons 4.11.0, OIDC SSO 4.6.0 and SAML 4.2.1.
   `marketplace/scratch.go` already builds a throwaway project at a chosen
   Mendix version and imports a package into it, so the harness exists.

2. **Sample apps and industry templates.** The marketplace publishes whole
   applications, not just modules — `marketplace.Content.Type` already carries
   `"Starter App"` alongside `"Module"`, `"Widget"` and `"Theme"`. These are far
   more complete than anything assembled from modules: real pages, workflows,
   microflow activity variety, integrations, security — authored by Mendix, in
   Studio Pro, and maintained per release.

   The likely mechanism is direct: `mx create-project` takes a **template
   `.mpk` as its positional argument**, which is how the Blank template is
   applied, so a starter-app package plausibly expands into a full project with
   one command and no Studio Pro. **This is untested** — mxbuild ships no
   template `.mpk` to try it against offline, and `mxcli marketplace install`
   deliberately does not auto-install this content type today
   (`cmd_marketplace_install.go` downloads it and says "import it via Studio
   Pro" rather than guessing a placement it cannot verify). Confirming it is a
   one-command experiment for anyone with marketplace credentials.

3. **Any real project a contributor already has.** The corpus checker should
   take a path, so a contributor can point it at their own app and contribute
   findings without shipping the app.

The constraint on 1 and 2 is **credentials**: marketplace access goes through a
PAT (`mxcli auth login`), so these cannot run in an unauthenticated CI job. The
practical split is therefore a **two-tier corpus** — the blank-app tier runs
everywhere on every commit, and the marketplace tier runs where credentials
exist and contributes findings that are then pinned into tests as embedded
fixtures, exactly as the regex and scheduled-event codecs already do. Pinning
the findings, rather than depending on the download, is what keeps the evidence
reproducible for contributors who have no marketplace account.

## 5. Decision

**Do not vendor engalar's generator.** It would let us regenerate and would
reintroduce the 102 mismatches on every run, behind a `supplements.json` we
would then have to grow to 102 entries by hand — the same work as patching gen
directly, with an extra moving part.

**Fix a wrong key by hand, in `init<Type>`, with the evidence in the comment.**
Four such `STORAGE-NAME OVERRIDE` precedents already exist, and
`TestGeneratedCodeIsFormatted` exists *because* gen files get hand-edited. Two
rules, both already violated once:

1. **Patch both literals.** The encode key (`init<Type>`) and the decode key
   (`InitFromRaw`) are separate. Patching one yields a document that writes one
   key and reads another; the symptom is a confusing entity-rewrite refusal
   rather than a bad file.
2. **`gofmt` the file.**

**Do not fix all 102.** Most belong to types nothing writes, and a fix without
per-property evidence is a guess in the same class as the bug. The ledger in
`keyaudit_test.go` records them and fails on the two things that matter: a new
mismatch appearing (a re-vendored gen that silently dropped an override —
otherwise invisible until a user's document loses a property) and a listed one
being fixed without being struck off.

**`mx check` is a weak oracle here.** It caught the `RegExIdentifier` case as
CE0135, but it tolerates unknown properties in general, and Studio Pro is
stricter than mxbuild (CLAUDE.md, "Overlay Writes"). A green build is not
evidence that a key is right.

## 6. Proposed sequence

Ordered by dependency; each step is worth doing on its own. No step requires a
closed-source artefact.

1. **Corpus-check the ledger.** Build a blank project per supported Mendix
   version with the mxbuild we already download, walk every `.mxunit`, and
   record the property keys actually observed per `$Type`. Compare against
   `keyaudit_test.go`. This confirms or refutes up to 21 of the 65 entries from
   free, licence-clean, CI-able evidence, and gives the ledger a second source
   that is not `generated/metamodel`. *Cheapest step with the highest
   information gain.*
2. **Extend the corpus with marketplace content**, in two steps because the
   second is unproven:
   - **Modules**, via the existing `marketplace/scratch.go` path — the method
     already used for regular expressions and scheduled events.
   - **Sample apps / industry templates**, which are far more complete and are
     the best available proxy for a real application's type coverage. First
     confirm that a `"Starter App"` package expands via
     `mx create-project <template.mpk>`; if it does, one download yields more
     ledger coverage than every module combined, and `mxcli marketplace install`
     gains a real branch for a content type it currently declines to place.

   Both tiers need a marketplace PAT, so their findings must be **pinned as
   embedded fixtures** (the regex/scheduled-event pattern) rather than
   re-downloaded per run — otherwise the evidence is unavailable to any
   contributor without an account.
3. **Promote the audit to a build-time gate.** `keyaudit_test.go` already runs
   in `go test`; the remaining work is deciding whether a new mismatch fails CI
   hard, and re-pointing its expected side at corpus evidence where step 1 or 2
   supplies it. Independent of everything else.
4. **Confirm what `ped_get_schema` actually returns** — one call against a live
   Studio Pro, body kept, for a type where SDK and storage names differ
   (`DomainModels$Attribute` is the sharpest: `type` vs `NewType`). If it does
   carry storage names, it becomes a per-version type-wide source and steps 1–2
   become a cross-check rather than the primary. If it does not, record that and
   close the question.
5. **Then, optionally, an MCP-driven authoring harness.** Drive Studio Pro to
   create a construct and diff the resulting BSON, automating CLAUDE.md's manual
   "ask the user to build it in Studio Pro" loop. Developer-loop only — it needs
   Studio Pro on Windows/macOS, so it cannot be a build step.
6. **Emit the codec shape from our own generator — only if an open input exists.**
   A second emitter on `cmd/codegen` would make all 102 correct by construction
   and fold in the `TypeVersionInfo` type-level bound fix. It is the largest item
   by far, and it is **blocked on having a licence-clean, complete type source**;
   steps 1–4 decide whether one exists. Do not start it on the strength of three
   confirmed properties out of 102.
7. **Report upstream.** The ledger is a concrete bug list against Mendix's own
   SDK-to-storage mapping, and the real fix belongs in the generator, wherever
   it is maintained.

## 7. What this does not change

- No change to the engine split, the backend interface, or ADR-0004/0005.
- No change to `modelsdk/gen`'s versioning model — it stays version-parametric.
- Existing `STORAGE-NAME OVERRIDE` patches stay as they are.

## 8. Open questions

1. **Does `ped_get_schema` carry storage names?** §4A.1 argues it does not, from
   PED's wire format, but that is inference. One call settles it. If it does,
   it is the per-version, licence-clean, type-complete source this whole problem
   wants — so it is worth answering early even though the argument runs against
   it.
2. **Is there any other licence-clean, type-complete source?** The metamodel does
   live in the modeler assemblies (ADR-0008 notes `IsIdentifier` is reachable
   only there) inside a distribution we already download per version. Whether
   reflection over those assemblies is permissible, and practical from Go, is
   unexamined.
3. **How many of the 102 matter?** A cheap first pass: intersect the ledger with
   the `$Type`s mxcli actually writes. A wrong key on a type nothing writes
   costs nothing.
4. **What is the real corpus coverage?** §4A.2 measures 21 of 65 ledgered types
   present in a blank 11.13 project, but presence of a `$Type` does not imply
   presence of the mismatched property. Step 1 of §6 produces the true figure.
